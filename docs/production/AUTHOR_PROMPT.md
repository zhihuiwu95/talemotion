# 给故事制作模型的任务提示

把下面这段任务连同 `FOURTH_STORY_BRIEF.md` 交给你选择的模型。模型应能访问本仓库并执行本地命令；只有聊天能力时可先交付 JSON，由用户在仓库运行检查，必须标明执行由谁完成。

---

你负责用 TaleMotion 已有能力制作一个新的亲子互动故事。先读 `docs/production/README.md`、`STORY_STANDARD.md`、`CAPABILITIES.md`、`EVALUATION.md`、`FOURTH_STORY_BRIEF.md`，以及 `src/stories/evidence.json` 和三个 `src/stories/packs/*.json` 样板。结构不明确时查 `docs/production/story.schema.json`。

这是有限范围的故事制作任务。请保留现有工作区修改，不重写播放器或原故事，不修改测试、校验器、能力目录和证据目录来让新故事通过。不创建新的模型编排系统，不生成第四个故事之外的内容。新需求超出现有能力时，提交具体缺口报告并说明完成状态。

按以下顺序完成，不要反复向用户确认已经明确的日常制作步骤：

1. 检查工作区状态，记录本次文件范围；读取第四个故事任务书。写出简短选题卡与梗概，明确一个主要目标、角色的具体愿望、孩子为何参与、来源和教育依据的适用边界。
2. 在 `docs/production/runs/fourth-story-draft.md` 写互动分镜：画面、台词、可操作对象、可见后果。先自查角色动机、情节因果和自由选择，不要用随机答题填充操作。
3. 生成一个严格符合规范的 `src/stories/packs/garden-gathering.json`。从能力目录选择资产、位置、动作和情绪；没有能力就报告缺口，不能虚构 ID。提供至少两条覆盖全部节点与选择的 acceptance 路径。
4. 运行 `npm run stories:validate`。把首次结果记入评测表，再做至多两轮针对性修复；保留每轮错误摘要。仍不通过时说明具体缺口，不降低规则、不虚报完成。
5. 运行 `npm run stories:review`，审看新分镜的场景状态是否真的实现 consequence 中承诺的结果。台词审阅通过后运行 `npm run audio:generate`；密钥只由本机环境提供，禁止读取或展示完整 shell 配置和密钥值。
6. 运行 `npm run quality`；在浏览器实际走过新故事的全部结尾，检查手机布局、连击、静音、声音、暂停与重玩。没有浏览器工具时明确把此项标为“待用户验证”，不能写通过。
7. 复制 `docs/production/EVALUATION.md` 的记录模板到 `docs/production/runs/fourth-story-result.md`，填写模型标识、用时、首次通过情况、修复次数、费用（不可取得则写未知）、人工修改与限制。输出本地试玩链接、修改文件和未完成项。不要自行提交、推送或部署。

允许新增：新故事 JSON、上述两份运行记录；允许工具更新：`src/generated/narration.json`、新音频文件、自动分镜文档。前三个故事和运行时代码保持原样。不要删除历史音频缓存。

故事品质要求：有故事动机、有可见后果；自由选择没有错误答案；角色可以表达“我还没玩完”；反馈简短具体，无羞辱或强制分享；不把完成故事当作能力或品德证明。引用已有证据只支持设计方向，不写本游戏已被科学验证。

---

成本控制：先文字与数据、后音频；失败只修改相关节点。无需把整个仓库或全部历史聊天塞入每次提示。验证阶段使用相同规范与样板，记录所有额外提示；不要在运行后悄悄改变验收标准。
