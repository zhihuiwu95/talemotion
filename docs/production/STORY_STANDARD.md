# 故事生产规范 v1

这是一份经三个工程样板试用的项目规范，不是行业标准或经实验验证的教学法。数量、时长、字数是产品起始约束，后续以试玩观察调整。

## 输入与输出

输入：目标年龄和能力范围、一个主要目标、题材或合法来源、现成角色与演出能力、有限制作预算。缺少孩子具体能力时，按样板的 3–4 岁亲子共玩定位制作，并写明成人支持方式。

输出：一个原创或有明确改编许可的故事 JSON、自动导出的分镜、生成的配音，以及真实填写的验收记录。第四个故事独立评测时不修改前三个样板或播放器。

制作顺序：选题卡 → 故事梗概 → 互动分镜 → JSON → 校验/审阅 → 语音与预览 → 工程验收 → 家庭试玩。前半程发现剧情问题时先改文字，避免提前花费图片、语音成本。

## 选题与依据

每个故事的 `learning` 必须给出一个可观察的主要目标、依据 ID、设计理由、观察方法、生活延伸与效果边界。不得写“全面提升智力”“科学证明这个故事有效”。

依据目录是 `src/stories/evidence.json`。指导性文件支持设计方向，研究支持某类设计的可能收益或风险；两者都不是当前产品的学习效果证书。模型只能引用已有 ID；新依据需单独核对原文、适用年龄、研究对象与限制后再入库。不能为了通过校验编造论文 ID。

推荐来源：教育部《3—6岁儿童学习与发展指南》、NAEYC 适宜性实践原则。互动设计参考 Takacs 等 2015 年的电子故事元分析，尤其注意热点和小游戏可能打断理解。原始链接与适用限制见依据目录。

素材来源可用项目原创，或经逐本核实许可的开放绘本。Book Dash 官方提供[改编与署名说明](https://bookdash.org/re-using-the-book-dash-content/)，StoryWeaver 提供[开放许可说明](https://storyweaver.org.in/en/open-content)。开放许可不等于教育品质认证。

`provenance` 记录原作标题、原作链接、许可、署名和改编内容。改编必须有精确来源链接；程序只检查字段，不判断许可真实性。旧故事原文、现代译文、插画与录音的权限分别核对。原创稿记录 AI 辅助与实际审核状态，不伪称专业团队背书。

## 故事与互动

建议从 1 个主要困难、2 位主要角色、4–8 次有意义的操作开始。单条台词硬上限 64 个字符，通常用 1–2 句短话；不是科学规定的注意力极限。v1 允许 4–24 个节点，每幕最多 3 个可操作对象，通常 1–2 个。

每个互动都要写清楚：角色为什么需要它、孩子凭什么发现线索、能做什么、结果在画面上怎样出现。不要为了达到操作数量插入题卡；也不要只让所有按钮跳到一段相同的赞美。

| 互动类别 | 规范 | 例子 |
|---|---|---|
| `goal` | 有具体物理或感知目标，可重试；提示描述差异和下一条线索 | 比较条纹手套 |
| `free` | 每个选项均成立；全部使用 `choice` 后果，不能判错 | 棚顶颜色、轮流或拍手 |
| `explore` | 探索与故事有关；不因没发现彩蛋卡住主线，不判错 | 小鸟指出积雪线索 |

错误尝试不扣分、不责备，不能把“善良/听话”设置成唯一正确答案。自由选择可以汇合，但至少先有不同的角色回应或可见状态。角色可以说“我还没玩完”；分享和参与不作为品德考核。

鼓励用“简短愉悦 + 具体行为或后果 + 角色回应”。例如“你找到一样的条纹啦！手暖和了，谢谢你！”允许“你真棒”，避免每一步都堆叠赞美，避免聪明/笨的能力标签、夸大承诺或让孩子负责角色的长期幸福。

故事可以拟人化，但自然事实不能误导。小雨棚样板明确是玩具级搭建，不教授儿童建造可承重结构。生活延伸需要成人陪伴；不把游戏结果表述为真实科学实验结论。

## 数据契约

机器结构见 `story.schema.json`，实际权威是 `src/stories/schema.ts` 与能力枚举。JSON Schema 导出不包含全部图语义规则，因此必须运行 `stories:validate`。

- 根对象：`schemaVersion/catalogVersion/id/title/summary/theme/audience/provenance/learning/start/nodes/acceptance`。
- `id`：小写英文及数字、连字符，首字符字母，最长 48；不得占用原活动 ID；所有故事 ID 唯一。
- 节点：`id/kind/backdrop/entities/line/cue`；交互节点有 `interaction`，演出节点有 `next`，结尾两者都没有。
- 实体：`id/asset/slot/mood/motion`；一个节点内实体 ID 和 slot 各自唯一。每个节点是完整画面快照，未列出的实体消失，不继承上一幕隐藏状态。
- 台词：`speaker/text/style`；speaker 是字幕署名，v1 仍使用同一个晓晓多语言声线，不能因此声称多角色音色。
- 选择：`id/target/label/next/outcome/consequence`；target 必须是本幕可见实体；label 是按钮与读屏名称；consequence 是人工审阅用的可见后果描述，程序不会自动把它变成动画。
- `interaction.reason`：说明此处为什么需要孩子参与。`outcome` 是制作语义，不显示分数。
- `acceptance`：给出 choice ID 序列和预期结尾。自动演出不写进选择序列。所有节点、所有选择必须至少被一条用例覆盖。

`interactive` 在台词结束后等待用户；`beat` 在声音和最短演出时间都完成后自动进入 next；`ending` 等待用户主动重玩或退出。重试可以经过提示演出返回选择；不允许自动循环，也不允许出现到不了结尾的交互死路。

禁止嵌入 JavaScript、HTML、CSS、SSML、任意 URL 资源或未列出的动作。需要新能力时输出缺口报告，不能修改 schema 或放宽校验掩盖问题。

## 统一交互与配音

连击保护、暂停、后台暂停、重听、静音、超时释放、退出清理全部由播放器提供。故事作者不配置“下一步解锁时间”，不复制组件。关键动作最长 1.7 秒；统一最短停留 1.8 秒，同时等待配音完成。20 秒音频看门狗用于故障恢复，不是正常故事节奏。

静音保留最短演出时间。暂停冻结动画并取消音频，恢复重播当前台词。重玩从 start 开始清空内存中的历史；没有自动开下一集。声线与 SSML 参数由现有 Azure 工具统一控制。仅在台词审阅后生成，按内容和风格缓存。

同一段台词若要两种语气，应先修改文案使语义区别明确；现有音频以文本索引，采集器拒绝同文不同 style。不要假定字幕 speaker 会改变音色。
